# Шестисторонний тоннель считывания штрихкодов

Учебный проект для тестового задания Ozon, вариант 2. В папке лежат две связанные
части:

1. инженерное предложение по реальному устройству (файл `report.pdf`);
2. запускаемый Python-прототип, который собирает события от нескольких
   считывателей, относит их к коробке, убирает повторы кадров и формирует один
   результат для системы сортировки.

Я специально не изображаю промышленную камеру обычной веб-камерой. В выбранной
архитектуре распознавание выполняют smart-reader'ы Cognex, а этот код показывает
ту часть алгоритма, которую действительно можно честно продемонстрировать без
физического стенда: синхронизацию, агрегацию, дедупликацию и передачу результата.

## Коротко о решении

Коробка проходит через затемнённый тоннель. Семь считывателей смотрят на шесть
граней: верх, левую, правую, переднюю, заднюю и двумя ракурсами на низ. Нижняя
грань видна через разрыв между двумя короткими конвейерными секциями. Это важная
деталь: без разрыва или прозрачной ленты обещать чтение кода снизу нельзя.

```text
датчик входа ──> readers (7 шт.) ──Ethernet──> edge-компьютер
      │                  │                         │
      └──── box_id + положение по энкодеру ──────┤
                                                 ├─> OK + codes[]
                                                 ├─> NO_READ
                                                 └─> INCOMPLETE
                                                       │
                                                       └─> ПЛК/СУ конвейера
```

Предлагаемое production-оборудование:

| Узел | Модель и количество | Зачем |
|---|---|---|
| Считыватели | 7 × Cognex DataMan 3816X, 16 MP | Декодируют 1D/2D внутри устройства; 16 mm объектив даёт нужное поле зрения |
| Свет | HPIT white, поляризованная крышка | Короткий яркий импульс замораживает движение и подавляет блики от скотча |
| Датчики коробки | 2 × SICK WTB4FP-21311120ZZZ | События входа/выхода с реакцией менее 0,5 ms |
| Энкодер | SICK DFS60E-S4EA01024 + мерное колесо | Привязывает кадры к пройденному расстоянию, даже если скорость немного меняется |
| Edge-компьютер | OnLogic Karbon K410, Atom x6425E, 16 GB RAM, 512 GB SSD | Локальная агрегация; нейросеть и GPU не нужны |
| Коммутатор | Moxa EDS-G4012 | 12 гигабитных промышленных портов с запасом |

Числа, схемы размещения, расчёт смаза, метрики и план испытаний находятся в
`report.pdf`.

## Быстрый запуск без установки зависимостей

Нужен Python 3.11 или новее. Из корня проекта:

```bash
PYTHONPATH=src python3 -m barcode_tunnel simulate \
  examples/events.jsonl --config config/tunnel.json
```

В ответе должны быть:

```json
{
  "box_id": "OZON-DEMO-001",
  "status": "OK",
  "unique_codes": ["24652856131000", "BOX-SECOND-CODE"],
  "occurrence_count": 3
}
```

Почему уникальных значений два, а физических наклеек три: код
`24652856131000` встречается на одной грани в двух далёких координатах. Повторный
кадр первой наклейки удаляется, но вторая наклейка с таким же текстом остаётся.
Для сортировки отправляются и `unique_codes`, и подробные `occurrences`.

## Тесты

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

Тесты проверяют:

- удаление повторов между соседними кадрами;
- сохранение двух одинаковых кодов в разных местах одной грани;
- `NO_READ`, если шесть граней просмотрены, но кодов нет;
- `INCOMPLETE`, если одна или несколько граней не подтверждены;
- привязку события к коробке по временному окну;
- HTTP health-check и приём события.

## HTTP-режим

Запуск:

```bash
PYTHONPATH=src python3 -m barcode_tunnel serve \
  --config config/tunnel.json --host 127.0.0.1 --port 8080
```

Проверка:

```bash
curl http://127.0.0.1:8080/health
```

Начало коробки:

```bash
curl -X POST http://127.0.0.1:8080/v1/events \
  -H 'Content-Type: application/json' \
  -d '{"type":"box_started","box_id":"BOX-42","at":"2026-09-17T12:00:00Z"}'
```

Результат после `box_finished` можно запросить так:

```bash
curl http://127.0.0.1:8080/v1/results/BOX-42
```

Если в `config/tunnel.json` заполнить `callback_url`, итог автоматически уйдёт
POST-запросом в систему управления. Заголовок `Idempotency-Key` равен `box_id`,
поэтому повторная доставка не должна создавать второе решение о сортировке.

## Формат событий

Общие правила: время — ISO-8601 с часовым поясом; координаты — нормированные
`x, y` от 0 до 1 в системе конкретной грани.

### `box_started`

Формируется входным фотодатчиком. `box_id` может прийти от ПЛК или быть создан
агрегатором.

```json
{"type":"box_started","box_id":"BOX-42","at":"2026-09-17T12:00:00Z"}
```

### `face_observed`

Reader закончил окно съёмки грани, даже если ничего не декодировал. Благодаря
этому `NO_READ` отличается от сломанной/неувиденной камеры (`INCOMPLETE`).

```json
{"type":"face_observed","box_id":"BOX-42","reader_id":"top-01","face":"top","at":"2026-09-17T12:00:00.100Z"}
```

### `reading`

```json
{
  "type": "reading",
  "box_id": "BOX-42",
  "reader_id": "left-01",
  "face": "left",
  "code": "24652856131000",
  "symbology": "CODE128",
  "position": {"x": 0.20, "y": 0.40},
  "quality": 0.96,
  "at": "2026-09-17T12:00:00.220Z"
}
```

### `box_finished`

Формируется выходным фотодатчиком или по позиции энкодера.

```json
{"type":"box_finished","box_id":"BOX-42","at":"2026-09-17T12:00:00.800Z"}
```

## Статусы и безопасная логика

| Статус | Условие | Действие конвейера |
|---|---|---|
| `OK` | Все шесть граней подтверждены и найден хотя бы один код | Сортировать по `unique_codes` |
| `NO_READ` | Все грани подтверждены, кодов нет | В отвод на ручную проверку |
| `INCOMPLETE` | Нет подтверждения грани или обязательного reader'а | В отвод; создать диагностику reader'а |

Система не может математически доказать, что прочитала **все** наклейки, если
заранее неизвестно их количество. Поэтому безопасная стратегия состоит из
полного покрытия граней, контроля здоровья каждого reader'а и отдельной линии
исключений. На испытаниях измеряется package read rate на размеченной выборке.

## Опциональное декодирование изображения

Для локального эксперимента есть обёртка над ZXing-C++. Она не является заменой
промышленному reader'у.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[vision]'
barcode-tunnel decode-image photo.png --box-id BOX-42 --face front
```

Команда печатает события `reading` в JSONL. Для основного симулятора и сервера
эти зависимости не нужны.

## Как я рассуждал

1. Сначала я выписал физические ограничения: 1 m/s, коробка до 600 × 400 ×
   400 mm, метка 78 × 25 mm, несколько кодов и любая грань.
2. Потом заметил проблему низа. Поэтому добавил transfer-gap и два нижних
   ракурса — иначе требование не выполняется.
3. Посчитал смаз: при 1 m/s и выдержке 75 μs коробка смещается на 0,075 mm. Это
   меньше характерной толщины узкого элемента кода и намного лучше длинной
   обычной выдержки.
4. Выбрал smart-reader, потому что он уже решает сложную часть 1D/2D и выдаёт
   результат по Ethernet. Edge-компьютеру не надо круглосуточно гонять семь
   видеопотоков.
5. В коде разделил «повтор кадра» и «вторая такая же наклейка». Для этого кроме
   текста кода используется грань и координата.
6. Добавил статусы ошибок. Отсутствие результата нельзя молча превращать в
   пустой список — сортировщик должен отправить коробку на ручной разбор.

## Ограничения прототипа

- Он принимает уже декодированные события, потому что реальных DataMan и
  конвейера в репозитории нет.
- Если reader не сообщает координату, две одинаковые наклейки на одной грани
  сольются в одну. В production координаты обязательны.
- Состояние хранится в памяти. Для эксплуатации нужны журнал на SSD, метрики,
  watchdog и восстановление после перезапуска.
- Перед закупкой обязателен оптический тест на реальных коробках. В задании не
  указаны минимальный размер модуля, качество печати, допустимый наклон,
  состояние скотча и перечень символогий.
- Механическую безопасность transfer-gap, ограждения, аварийный останов и
  соответствие локальным нормам должен подтвердить инженер по оборудованию.

## Структура проекта

```text
config/tunnel.json              грани, обязательные reader'ы, окно и callback
examples/events.jsonl           воспроизводимая демонстрация
src/barcode_tunnel/aggregator.py группировка и дедупликация
src/barcode_tunnel/server.py     HTTP API
src/barcode_tunnel/transport.py  доставка результата в СУ
src/barcode_tunnel/vision.py     опциональный ZXing-C++ адаптер
tests/                           unit- и HTTP-тесты
report.pdf                       инженерный отчёт
```
